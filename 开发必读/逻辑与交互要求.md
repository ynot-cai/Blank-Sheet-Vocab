## R1 · 任何考察都不得设置强制时间限制

**规则**：
所有考察环节（默写 / 拼写考察、任何题型考察、任何形式的答题），**一律禁止**任何强制时间限制。

**明确禁止**：
- ❌ 答题倒计时、剩余时间显示并倒计时归零
- ❌ 超时自动提交
- ❌ 超时判错 / 超时扣分
- ❌ "限时 N 分钟完成"的强制要求
- ❌ 任何形式的"时间到就怎样"

**明确允许**（这些不是违规）：
- ✅ 网络请求的超时保护（`AbortController`、fetch timeout）
- ✅ 防抖节流（同步调度、搜索防抖）
- ✅ 动画、过渡计时
- ✅ 纯信息展示的"已用时 X 分"（**仅展示，不强制、不判错**，且默认关闭）

**理由**：用户明确要求。思考型作答需要时间，限时只会制造焦虑、不提升学习效果。

**代码要求**：任何涉及答题流程的文件，在关键位置加注释标记：

```ts
// RULES-R1: 此处禁止任何强制时间限制（无倒计时 / 无超时提交 / 无超时判错）
```

## R2 · 义项系统规则（录入 + 判分）

### 2.1 录入时的义项规则

1. **含义相近的中文意思合并为一个义项**，选定一个**代表义项**，其余作为**近义词**存入该义项的 `aliases`
   - 例：「高兴 / 快乐 / 愉快」→ 一个义项，代表「高兴」，aliases = ["快乐","愉快"]
2. **确实不同的意思必须拆开**
   - 例：「bank → 银行 / 河岸」是两个独立义项
3. 音标、例句缺失时由 AI 补全
4. **等价关系（哪个是代表、哪些算近义词）在录入时确定并固化**，后续判分按这个来

### 2.2 考察时的判分规则（用户明确定义的合格标准）

> **看到多义词 / 多词性的单词，要对它的每一个义项分别作答（纯中文）。**
> **若作答匹配该义项的代表义项，或匹配其任一近义词，即算该义项通过。**

具体要求：
- 一个词有几个义项，就给**几个输入框**，逐个考察，**不能只考其中一个**
- 用户作答用**纯中文**
- 匹配判定：命中代表义项 **或** 命中 `aliases` 中任一近义词 → 通过
- 近义词的等价关系来自录入时的固化结果，不是考的时候临时判断

## R3 · 「斩」不弹确认，但必须可撤销

**规则**：
- 斩操作**不弹二次确认框**（直接生效）
- 但必须提供**撤销**入口：斩后立即显示 Toast「已斩 XXX 〔撤销〕」，**撤销窗口 ≥ 8 秒**
- 列表页的「已斩」分区可随时复活（永久后悔药）

**理由**：确认框打断流程，撤销条更顺手；两者结合既快又不怕误触。

**代码要求**：斩相关代码处加注释：

```ts
// RULES-R3: 斩不弹确认，但必须提供 ≥8 秒的撤销 Toast
```

## R4 · 安全底线（继承，重申）

1. **服务器永不接触 AI 密钥**（方案 B）：不得有存储密钥的逻辑，不得有存密钥的表
2. **只存哈希**：同步码只以 SHA-256 哈希落库
3. **空间隔离**：所有 SQL 必须带 `WHERE space_key = ?`
4. **本地优先**：同步失败只轻提示，绝不阻断使用
5. **不渲染 AI 输出的 HTML**：只能解析为结构化数据后用 `textContent` 渲染

## 第 4 节 · 运行时 AI 提示词必含片段（给录入/出题模型）

> **dsh 注意**：以下两段文字必须**原样**出现在对应提示词模板里，自检脚本会检查是否包含。
> 代码里的机器可引用副本在 `src/services/promptRules.ts`，两边**逐字**相同，
> `npm run test:r4` 会逐字比对，差一个字符就红。

### 4.1 录入解析提示词必须包含（完整）：

```
【义项处理规则 - 必须严格遵守】
1. 含义相近的中文意思合并为一个义项，选一个最常用的作为代表义项，
   其余作为近义词(aliases)。例：「高兴/快乐/愉快」→ 一个义项，
   代表「高兴」，aliases = ["快乐","愉快"]
2. 确实不同的意思必须拆成不同义项。例：「bank → 银行 / 河岸」是两个义项
3. 音标、例句缺失则补全
4. 只为多义词/多词性单词建立多个义项；单义词只建一个
5. 输出严格 JSON
```

### 4.2 出题提示词必须包含（完整）：

```
【出题约束 - 必须严格遵守】
1. 不得设置任何时间限制、倒计时、限时完成要求
2. 生成的题目中不得出现"请在 X 分钟内完成"等表述
3. 题目应鼓励思考，不鼓励抢答
```

## 第 5 节 · 界面与运行逻辑要求（用户指定）

> 本节是**要求**，不是现状。写代码前先确认实现与本节一致；不一致就是 bug。

### 5.1 现行界面边界（版本 0.0.1 起生效）

| 要求 | 具体含义 |
|---|---|
| **主界面只保留「设置」按钮** | 顶栏与主页都**只有一个**「设置」入口。任何新增入口都要先问用户。 |
| **设置页只保留三项** | ① 同步 ② AI 接口 ③ 复习优先度计算公式。其他设置项一律不出现。 |
| **允许保留分类外壳** | 允许存在「画面设置」这类**可展开收起的空壳**用于标示位置感，但**壳内不得有具体设置项**（除非属于上述三项）。 |
| **数据层完整保留** | 一个单词有哪些属性（`core/types.ts` + `core/model.ts`）、单词存在哪（`core/dbSchema.ts` + `dao/words.ts`）、数据同步（`dao/cloudSync.ts` + `dao/syncServer.ts` + `api/`）三者**一个字段都不许少**。 |
| **不保留无入口的页面** | 页面模块若已无入口，必须「先归档、再从原位置删除」，不留死路由。 |

### 5.2 数据与同步逻辑（不可动摇的部分）

1. **本地优先**：所有数据先落本机 IndexedDB（库名 `blank-sheet-vocab`）。断网、后端挂掉都必须能照常使用。
2. **同步是加法，不是依赖**：云同步默认关闭；开启后数据变动防抖同步。同步失败只轻提示，**绝不阻断任何操作**。
3. **空间隔离**：同一套后端服务多个人用，靠用户自编的「同步码」区分空间；每条 SQL 必须带 `space_key`。
4. **服务器零密钥**：AI 密钥只存在用户本机浏览器；服务端代理只做转发，不落库、不记日志。
5. **数据结构由迁移推进**：库结构变更一律走 `onupgradeneeded` 的幂等迁移（`core/dbSchema.ts`），**老数据一条都不许丢**。
6. **删除是墓碑**：词条删除（斩）在本地与云端都留语义痕迹，保证多设备之间「删了就是删了」。

### 5.3 交互细节要求

1. **复习优先度是「可预测」而不是「随机」**：抽词按优先度**绝对优先**排序，同级内再按可复核的次序（默认先录入的先背）。
2. **优先度公式允许用户自定义**：设置页「复习优先度计算公式」提供预设 + 自定义表达式两条路。自定义表达式必须走三层安全边界（字符集白名单 → 变量白名单 → **真试算一次**），非法表达式必须**回退到预设**而不是让全库优先度变 0。
3. **判分基于录入时固化的等价关系**（见 R2），可离线、可解释。
4. **任何破坏性操作都要有后悔药**：斩可撤销（R3）；数据删除要有明确的二次确认。
5. **中文界面**：所有面向用户的文案一律中文，且不得夸大或含糊（文案必须与代码事实一致）。

### 5.4 文档与归档要求

项目根目录除程序本身外，**只保留三个文件夹**，各自职责固定：

| 文件夹 | 职责 | 内容要求 |
|---|---|---|
| **已归档** | 归档历史 | 保存废除但仍有参考价值的改动，以一个个「拔出的模块」形式存放。每份文档必须写明：这是什么、什么版本被归档、为什么归档、被谁引用、怎么恢复，并附完整源码。 |
| **关于项目** | 说明项目现状 | 两个文档：`版本更新日志.md` 与 `项目概述.md`。 |
| **开发必读** | 说明项目要求 | 两个文档：`逻辑与交互要求.md`（本文件）与 `开发规则.md`。 |

**归档的三条硬要求**：
1. **先归档、后删除**——归档文档写出来并自检完整之前，不许删任何源文件；
2. **删除必须可恢复**——一律走 Windows 回收站（`Microsoft.VisualBasic.FileIO.FileSystem.DeleteFile` + `SendToRecycleBin`），不许用永久删除；
3. **删除集合必须等于归档集合**——删除清单要从归档文档里解析出来，不许手工维护。

## 第 6 节 · 自检脚本

项目根目录有 `scripts/checkRules.mjs`，运行：

```bash
npm run rules:check
```

它会自动检查：
- 本文件是否存在、是否含 R1~R4 四条规则
- 第 4 节的两段必含片段是否原样出现在提示词模板里
- 是否出现可疑的答题计时代码（列出供人工确认）
- 斩操作是否还有二次确认框
- 是否有「存储 AI 密钥」的表定义、业务表 SQL 是否都带 `space_key`

**每次改动考察/录入相关代码后必须跑一次，必须为全绿。**
报告里的 WARN 不算失败，但必须人工确认。
