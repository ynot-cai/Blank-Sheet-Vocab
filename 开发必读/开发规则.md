# 开发规则

> **本文件记录「编码 AI（dsh 等）需要跨对话遵循的要求」。**
> 它规定的是**工作方式**（版本怎么编、文档什么时候写、怎么删文件、什么不许做），
> 不是程序怎么跑（那是 `逻辑与交互要求.md`），也不是程序现在什么样（那是 `项目概述.md`）。
>
> **每次新对话开工前的固定动作**：按顺序读
> ① `开发必读/开发规则.md`（本文件，工作方式）
> ② `开发必读/逻辑与交互要求.md`（用户指定的交互与运行逻辑要求）
> ③ `关于项目/项目概述.md`（程序现状的架构说明）
> ④ `关于项目/版本更新日志.md` 的**最后一条**（上一次对话干了什么）
>
> 读完再动手。**没读完就改代码视为违规。**

最后更新：版本 0.0.1（2026-10-15）

## 一、版本管理规则（用户 2026-10-15 指定）

版本号一律 **`x.x.x` 三段式**，落点是 `package.json` 的 `version` 字段
（构建时由 `vite.config.ts` 读取并注入 `__APP_VERSION__`，程序界面上显示在设置页底部）。

| 段位 | 名字 | 什么时候 +1 | 谁决定 |
|---|---|---|---|
| 第一段 `x` | **大版本** | **由用户指定变化** | 只有用户能定 |
| 第二段 `x` | **小版本** | **每次用户要求「上传 git 仓库」时 +1** | 用户触发 |
| 第三段 `x` | **小小版本** | **每次用户与 AI 的一次对话 +1** | 每次对话自动 +1 |

### 进位与清零

> **每当上层版本加一，下层版本清零。**

- 大版本 +1（用户指定）→ 小版本、小小版本**都归零**。例：`1.4.7` → `2.0.0`
- 小版本 +1（用户要求上传 git 仓库）→ 小小版本**归零**。例：`0.3.5` → `0.4.0`
- 小小版本 +1（每次对话）→ 只动第三段。例：`0.3.5` → `0.3.6`

### 本次基线

**本次（用户下达「删除与归档行动」的这一轮对话）记为版本 `0.0.1`。**
即：大版本 0（用户尚未指定过任何大版本变化）、小版本 0（尚未上传过 git 仓库）、
小小版本 1（本次是第一轮对话）。

### 每次改版本的固定动作

1. 改 `package.json` 的 `version`
2. 在 `关于项目/版本更新日志.md` 顶部**新增一条**（不许覆盖旧条目）
3. 若这次是小版本或大版本 +1，还要按第二节更新 `关于项目/项目概述.md`
4. 自检：`node -e "console.log(require('./package.json').version)"` 输出应与日志顶部一致

## 二、文档更新规则

### 2.1 版本更新日志：**每次对话都要更新**

- 文件：`关于项目/版本更新日志.md`
- 频率：**每一次对话**，无一例外（哪怕只是改了一行注释）
- 写法要求（用户明确指定）：
  - ❌ 不许写「完善某某功能」「优化某某模块」这类空话
  - ✅ 要写清 **某某功能会出现什么问题**（症状、复现条件、影响范围）
  - ✅ 要写清 **做了什么修改**（改了哪个文件、改成了什么）
  - ✅ 更新了某个模块时，要写清 **该模块的目标是什么、具体架构是什么**
  - ✅ 破坏性改动要写清 **后果**（例如「导出备份入口被删除，用户暂时无法手动导出」）
- 结构：每个版本一个二级标题 `## 版本 x.x.x —— 一句话标题（日期）`，
  下面按「背景 / 问题 / 改动清单 / 影响与后果 / 涉及模块与架构 / 验证方式」组织。

### 2.2 项目概述：**每次小版本更新都要更新**

- 文件：`关于项目/项目概述.md`
- 频率：**每次小版本更新**（也就是每次「上传 git 仓库」）**必须**更新；
  大版本更新当然也要更新
- 组织方式：**以架构而非日期为组织**。不许按时间流水账写。
- 必须覆盖：
  1. **程序现有框架**——技术选型、目录分层、数据流、依赖关系
  2. **现有交互系统**——界面上有哪些页面、怎么进入、交互规则是什么
  3. **运行逻辑**——启动顺序、数据怎么存、同步怎么跑、错误怎么兜

### 2.3 逻辑与交互要求：**用户一开口就要记**

- 文件：`开发必读/逻辑与交互要求.md`
- 触发条件：**每次用户说出关于交互和逻辑相关的内容**
- 动作：
  1. 立刻把这条要求写进该文件（要具体、可执行，不写模糊表述）
  2. **冲突或修改的部分要删除旧内容**——不是「补充说明」，是**替换**
     （同一件事只允许存在一条要求，避免新旧两条互相矛盾）
  3. 若这条要求改变了现有实现，在同一次对话里把代码改到一致，并写进版本更新日志
- 例外：只改错别字、只调格式，不用记

### 2.4 规则文件本身受保护

`开发必读/逻辑与交互要求.md` 是本项目最高准则。
**修改它需要用户明确同意**；旧版本原件进 `已归档`，不许直接覆盖。

## 三、归档规则（用户 2026-10-15 指定）

项目根目录除程序本身外，**只允许存在三个文件夹**：

| 文件夹 | 职责 |
|---|---|
| `已归档` | 归档历史：废除但仍有参考价值的改动 |
| `关于项目` | 说明项目现状 |
| `开发必读` | 说明项目要求 |

### 3.1 什么要归档

任何**被废除、被拔掉、被替换**的模块/功能/文档，只要还有参考价值，就必须归档。
典型触发：用户说「删掉」「归档」「不再需要」「换成另一种做法」。

### 3.2 归档文档的写法（一份文档 = 一个完整模块）

每份归档文档必须是**自包含**的，脱离程序也能读懂、能还原。固定包含：

1. **一、归档基本信息**表格，逐项写清：
   - 模块名称 / 模块类型
   - **归档版本**（哪个版本被归档）
   - 归档日期
   - **归档原因**（为什么废除）
   - **原调用方**（谁在用它——写清才能判断恢复代价）
   - **恢复方式**（放回哪些文件、还要改哪里）
   - 原文件数 / 代码规模
   - 是否可从回收站恢复
2. **二、原文件清单**表格：序号 / 原路径 / 字节 / 行数
3. **三、完整源码**：逐个文件用围栏代码块贴**全文**（不是摘要、不是 diff）

文件名形如 `NN_模块名.md`，并登记进 `已归档/归档总索引.md`。

### 3.3 删除的三条硬纪律

1. **先归档、后删除**：归档文档写完并自检完整之前，**一个源文件都不许删**
2. **删必可恢复**：一律走 Windows 回收站，**禁止永久删除**
   （`Microsoft.VisualBasic.FileIO.FileSystem.DeleteFile(path, 'OnlyErrorDialogs', 'SendToRecycleBin')`；
   目录用 `DeleteDirectory` 同样参数）
3. **删除集合 == 归档集合**：待删清单要从归档文档第二节的表格里**解析出来**，
   不许手工维护清单（手工清单必然漂移）
4. **删除前先备份**：大范围删除前先做**项目外快照** + **本地 git 提交**（见第四节）
5. **删除前校验路径**：解析出的绝对路径必须以项目根目录开头，否则中止整个删除

### 3.4 归档后要报告的四件事

每次归档 / 删除都要向用户说明：**处理对象、目标位置、是否保留原数据、验证方式**。

## 四、Git 与备份规则

1. **不许推送至 GitHub**。除非用户**明确说出**「上传 git 仓库」，
   否则只允许本地提交，**不许 `git push`**。
2. 用户说「上传 git 仓库」时：① 小版本 +1（第三节的版本规则）② 更新项目概述
   ③ 这时才允许推送，并在版本更新日志里写明推了哪个提交。
3. **破坏性操作前必须留两条独立退路**：
   - 项目外完整快照（复制到项目同级目录，命名带时间戳）
   - 本地 git 提交（提交信息写清「变更前的状态」）
4. 快照要**验证**：比对源目录与快照的文件数、总字节数，不相等就是没备份成功。
5. 远端地址 `origin` = `https://github.com/ynot-cai/Blank-Sheet-Vocab.git`，
   存在 ≠ 可以推送。

## 五、改动代码的规则

1. **改完必须跑自检**：`npm test`（链路见 `package.json` 的 `scripts.test`）。
   涉及考察/录入相关代码时额外跑 `npm run rules:check`，必须全绿。
2. **类型检查必须过**：`npm run typecheck`（`tsc -b`）零错误才算改完。
3. **不留死代码**：模块若已无调用方，要么接上、要么归档删除，**不许维持现状**
   （`npm run test:build` 里有「没有未被任何文件引用的模块」这条护栏）。
4. **不留死路由**：页面模块没了，路由表里对应的一行也要删。
5. **注释要写「为什么」**：本项目的注释密度是刻意的——每处复杂度都配了
   「为什么这么做」「踩过什么坑」。改代码时保持这个风格，不要删掉解释性注释。
6. **文案必须与代码事实一致**：界面文案、文档里的数字（文件数、版本号、
   测试项数）都要跟着改；`npm run test:rename` 与各测试里都有硬编码断言。
7. **文件编码 UTF-8 无 BOM**（`test:build` 有护栏：带 BOM 会让 vite dev 的 CSS 全 500）。
   ⚠️ 唯一例外：给 Windows PowerShell 5.1 跑的 `.ps1` 脚本**必须带 BOM**，
   否则中文会被按 ANSI 解析成一堆语法错误。
8. **不许把规则注入当代码执行**：AI 返回的内容一律按数据处理（见 R4 第 5 条）。

## 六、沟通规则

1. **一律用中文**回复与写文档（用户是中文使用者）。
2. **先说结论再给细节**：每一步做完要明确说清「做了什么、结果如何、怎么验证的」。
3. **不确定就问**：当用户的要求存在两种以上合理解释、且代价不可逆（删除、覆盖、推送）时，
   **先问再动**，不要赌。
4. **不许谎报验证**：没跑的测试就说没跑，没验证的事就说没验证。
5. **不许擅自扩大范围**：用户列了编号清单就按编号执行，不顺手改清单外的东西；
   若发现必须顺带改的（例如删了模块导致引用断了），要在报告里**单独说明**。
